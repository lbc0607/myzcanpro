# CanVDS — UDS 诊断 / ECU 刷新上位机

基于 ZLG(USBCANFD / USBCAN-II)的自研诊断上位机,界面仿 ZCANPro。

## 运行(源码)
需 **32 位** Python(zlgcan.dll 是 32 位)+ PyQt5。ZCANPro 自带的 `python38` 即可:
双击 `run.bat`(路径不同时先设置环境变量 `PY32`)。
不接硬件时,通道选"模拟ECU(测试)"即可体验全部流程。

## 打包成绿色软件
- 本地:双击 `build.bat` → `dist\CanVDS\CanVDS.exe`(整个文件夹拷走即可)。
- 云端:推送到 GitHub 后由 `.github/workflows/build.yml` 构建,在 Actions 的 Artifacts 下载。

## 设备管理(主界面)
1. 下拉选择设备(USBCANFD 系列 / USBCAN-II / 模拟ECU),点「打开」→ 按钮变为「关闭」(只能在两种状态间切换)。
2. 打开成功后出现各通道行,点「启动」弹出配置:CAN/CAN FD、波特率(kbaud/s)、正常/只听、终端电阻、是否计算总线负载率(刷新时间默认 200 ms)。
3. 通道启动后,主界面实时显示接收/发送/错误帧数和总线负载率;软件扫描、普通发送等窗口只使用已启动的通道。

## 部署目录(与 exe 同级)
- `zlgcan.dll` 与 `kerneldlls\`:仓库 `vendor\` 里已带官方 SDK(zlgcan_x86,2026-10 版),打包时自动复制到 exe 旁;
  源码运行时程序也会自动在 `vendor\` 里查找。官方头文件在 `docs\zlgcan_sdk_headers\`。
- 公司密钥 dll 及其依赖;需安装 VC++ 2013 x86(zlgcan)、VC++ 2008 x86(密钥 dll)运行库
- 程序运行后自动生成:`CanVDS_config.json`(旧版 myzcanpro_config.json 首次启动自动读取)、`services.json`、`error.log`、`logs\`

## 例程控制(31)
在「软件扫描 → 添加功能」的步骤编辑器里选 31 服务后，先选「例程类型」，标识符(2 字节)、子服务(01/02/03)都由你填写：
- **擦除内存**: `31 [子服务] [标识符] [44] [起始地址] [大小] [扩展字节]`。格式字节高4位=大小长度、低4位=地址长度(与 ISO 14229 一致，默认 0x44)；
  起始地址、大小取自烧写文件，整个流程只执行一次；扩展字节(默认 01)可编辑或取消；大小可选「各段长度之和」(默认，与校验码工具的总长度一致)或「首段起始到末段末尾」。
- **CRC校验**: `31 [子服务] [标识符] [校验码]`。可选 *分段CRC*(每段传输结束后立刻校验，烧录结束后再做一次全文件CRC) 或 *全文件CRC*(只在烧录结束后校验一次)；
  全文件CRC 为各段按顺序拼接后的校验值。CRC 类型/字节序可配。
- **更新条件查询 / 自定义例程**: 任意 `31 [子服务] [标识符] [数据]`，数据可含占位符 `{addr} {len} {crc}`。

## 步骤与功能文件
功能（服务序列）为 JSON，保存在 `scan_data/<模块>/功能/` 下，各 SID 参数均可在步骤编辑器里编辑。**新增的服务/延时会插到当前选中步骤的下方**（没有选中则追加到末尾），不用再逐个上移。原「ECU刷新」「UDS诊断」界面已取消，用「软件扫描」里的功能编辑与「普通发送」代替。

## 测试
`python tests/run_all.py`(GUI 测试使用桩 Qt,不依赖显示环境)。

## 报文监视 (Message monitor)
主界面「报文监视」: 实时查看总线上的收发报文，可与 UDS 诊断 / ECU 刷新 / 普通发送同时使用。
- 通道的接收线程每读到一帧，同时交给 UDS 队列和监视器（被动旁听，监视器自己不读设备，不会抢帧，也不改变诊断时序）；发送帧在发送时记录。
- **按ID覆盖显示**（默认）: 同一 ID（通道+方向+ID+帧格式）一行，新帧覆盖旧帧，并显示计数；取消勾选则按时间顺序滚动（最近 1000 帧）。
- **时间差**: 「与同ID上一帧」或「与上一帧(任意ID)」。接收帧使用设备时间戳（保留真实间隔），发送帧用主机时间。
- **实时保存**: 后台线程把每一帧追加写入 CSV（含时间、通道、ID、类型、方向、长度、数据）；「保存」导出当前显示。
- 可按通道 / ID / CAN类型 / 方向 / 数据筛选；「暂停」只冻结显示，计数与保存不受影响。
- **错误帧**: 总线错误帧显示为红色的「错误帧」行（每通道一行，内容显示为 xxx），计数即错误次数，「时间差」即错误帧出现的间隔（频率）；取消底部「显示错误帧」可隐藏；滚动模式下每个错误帧各占一行。能否收到错误帧取决于设备/驱动是否上报。

## 软件扫描 (多核板上各软件的信息/功能)
主界面「软件扫描」: 对板子上的各个软件（动力域控制器 7E2、驱动电机控制器 7E3、电驱充电模块 7E3、从驱动电机控制器 745，响应=物理+8，功能 7DF）读取 软件编码 / 软件版本 / 硬件版本 / 故障码数量。
- **列表页**: 左侧勾选，底部「开始扫描 / 停止扫描」；未读取或读取失败显示 `-`；点软件名称改地址，点任一信息格子进入该项的「读取方式」编辑页；最右 `›` 进入该软件的功能页。
- **功能页**（上下级页面，不是弹窗，「‹ 上一级」返回）: 每个功能是一个按钮，点击即运行；「添加功能」进入编辑页（步骤编辑器：编排 UDS 服务），「新建文件夹」建子菜单（点进去就像进文件夹）；「管理」模式下点按钮可编辑 / 重命名 / 删除。
- **执行器 = 一个 JSON 文件**（服务序列 + 结果显示：取哪一步的回复、跳过开头几个字节，当前只支持十六进制原文）。例如读 VIN：`10 03` + `22 F1 90`，回复 `62 F1 90 XX…XX` 显示为 `XX…XX`。
- **数据文件夹**（默认程序目录下 `scan_data`，可在界面里改）的层级就是界面层级: `<软件>/module.json`、`<软件>/信息/软件编码.json…`、`<软件>/功能/…`。首次运行自动生成上面 4 个软件和默认执行器（默认读取命令: 软件编码 `22 F1 94`、软件版本 `22 F1 95`、硬件版本 `22 F1 93`，故障码数量 `19 01 08`；已存在的 scan_data 里的旧执行器不会被覆盖，要么在界面里改，要么删掉对应 json / 整个 scan_data 重新生成）。
- 扫描/运行时占用所选通道，期间其它窗口不能同时使用该通道（结束后自动释放）。

## 主界面布局
菜单（设备管理 / 软件扫描 / 普通发送 / 报文监视 / 校验码计算工具）在界面上方，点击后在界面内新开一个标签页（标签栏在下方，再次点击只切换到已打开的标签）；「设备管理」标签固定不可关闭。标签页右下角「⇱ 浮动」或双击标签可把该页变成独立窗口（窗口里「⇲ 停靠回主窗口」放回标签栏）。关闭标签即关闭该工具；正在刷写时会拒绝关闭。

## CAN FD 说明
- ISO-TP 单帧：≤7 字节的请求按经典单帧格式（`03 22 F1 90 ...`，8 字节 FD 帧）发送；8~62 字节才用扩展单帧头（`00 LL ...`）。早期版本把短请求也写成 `00 03 22 F1 90`，不符合 ISO 15765-2，ECU 不会应答。
- 「CANFD加速」在通道启动配置里（和 ZCANPro 一致）：选「否」时数据域沿用仲裁域波特率、所有 FD 帧不带 BRS；选「是」时数据域用所填速率、帧带 BRS。ECU 与总线上其它节点必须一致。「ISO-TP FD 帧长度」设为 8 则在 FD 通道上改发经典 CAN 帧（ECU 只认经典帧时用）。设置页里原来的「BRS」勾选和「模拟ECU 新/老产品」选项已删除（模拟 ECU 固定用 16 字节 seed）。

## 安全访问 (密钥 DLL 与 EcuSerialNum.txt)
**密钥 DLL 是全局配置**：在「更多设置 → 安全访问 → 密钥 DLL(全局)」选一次，保存在程序配置里**永久有效**（重启不用再选），所有功能里的「ECU解锁」步骤都用它，步骤里不再有 DLL 一栏（旧功能文件里已写了 dll 的步骤仍按它执行；相对路径按程序目录解析；`builtin:xor` 是演示算法）。agent 用 `set_settings(section='security', values={'key_dll': '路径'})` 设置。

计算密钥的 DLL（`ZLGKey`）每次调用都会读取**其工作目录**下的 `EcuSerialNum.txt`。文件名、所在文件夹（即 DLL 工作目录，默认=程序目录；可填绝对路径，也可点「python.exe所在文件夹」）、序列号 DID、格式、编号映射表都在「更多设置 → 安全访问」，**全程序共用一份并自动保存**（改一处处处生效，重新打开不会被功能文件覆盖；27 步骤里不再有单独的工作目录）。
- **第 1 行** 序列号：本次运行里**第一次**安全访问前用 `22 <DID>` 读取（默认 `F1 8C`，设置 → 安全访问 可改 DID / 文件名 / 序列号格式 ASCII 或十六进制）并写入；之后的安全访问（含其他 ECU）不再读取，第 1 行保持不变。ECU 消极应答 → 第 1 行为空（视为已读取，不再重试）；读取超时无应答 → 第 1 行为空，但下次安全访问会再试一次。
- **第 2 / 3 行** 软件编号：按**被解锁 ECU 的物理地址**查「设置 → 安全访问 → 编号映射表」，种子 2 字节时 DLL 取第 2 行，16 字节时取第 3 行。默认 `7E2:[0,0]  7E3:[1,2]  785:[2,4]  645:[1,3]`，可增删行；**物理地址不在表里会直接报错**（不发送、不写文件，避免错误密钥消耗 ECU 尝试次数）。
- 读序列号发生在 `27` 的 seed/key 事务**之前**且不占用请求锁，所以会话保活（3E 80）不受影响；seed 与 key 仍在同一个锁内连续完成。
- 程序启动时和退出时都会删除该文件；是否删除不影响正确性（"是否已读取"是每次运行的内存状态，第一次安全访问一定会重写第 1 行）。
- 原先在安全访问步骤里的「通过 F1 8C 写入序列号」勾选项已取消，以此处为准。旧的配置文件如果保存了旧的映射关系，请在设置表里核对。

## 日志与报文保存、普通发送次数
- **日志窗口只显示请求 / 响应（含否定响应）**；步骤横幅、"完成/信息" 行不再输出（步骤状态在刷写步骤列表里看）。出错信息（ERR）和「显示原始帧」打开时的 CAN 帧仍会显示。
- **实时保存按文件大小分片**（参考内部上位机的 MyLogRecord）：设置 → 高级设置 → 输出信息：日志文件夹（默认 `logs`）、单个文件最大 MB（默认 3，1~1024）、保留天数（默认 7，0=不删除，最大 3650）。超过大小自动写到 `xxx_1.txt / xxx_2.txt …`；报文监视的实时保存同样按大小分片（每片带表头）。自动命名的日志（`uds_ / flash_ / monitor_` 开头的 txt/csv，在日志文件夹里）超过保留天数在程序启动和开始保存时删除，其它文件不碰。「输出信息最大行数」上限 1,000,000，「单个文件最大行数」上限 10,000,000。
- **普通发送**：发送次数 1~100,000,000，**-1 = 一直发送**（点「停止」结束）；每次发送帧数 1~1000；间隔 0~3,600,000 ms。时间表按需生成，不再一次性展开（之前把次数设成几百万会占满内存导致崩溃）。串行模式下一直发送的行之后的行不会执行。

## 用对话操作 CanVDS（MCP，任何 agent 都能用）
agent 可以不开界面完成上位机的主要操作：设备/通道、UDS 诊断、自定义报文收发与监视、全局设置、软件扫描（含创建/执行功能）和 LIN 诊断。

**架构**：所有操作都在 `zdiag/ops.py`（统一操作层，和界面共用同一个设备管理器、设置、监视）；`zdiag/rpc.py` 把它开成**仅本机回环、带随机令牌**的 HTTP 端口；`mcp_server.py` 是这个端口的薄桥接。端口有两种来源：
1. **开在 CanVDS 界面里**：「设备管理」页的「Agent 接口」，默认打勾（随界面启动，可取消，记住你的选择）。agent 和你共用同一个设备，你能在界面上实时看到 agent 的操作（设备/通道状态、报文监视、最近操作）。
2. **无界面 daemon（不需要打开上位机）**：`python -m zdiag.daemon`（真机请用能加载 zlgcan.dll 的 32 位 Python）；MCP 服务发现没有端口时会**自动拉起一个**，agent 一连上就能直接操作，随 MCP 服务退出而退出。
> 同一设备只能由一个程序打开：界面和 daemon 不要同时运行（后启动的会被拒绝并提示）。

**启动 MCP 服务**（标准 stdio，需 Python ≥ 3.10）
```
pip install -r requirements-mcp.txt
python mcp_server.py
```
通用配置（各家客户端的 `mcpServers` 写法一致，路径改成你自己的）：
```json
{"mcpServers": {"canvds": {"command": "python", "args": ["D:/myzcanpro/mcp_server.py"],
  "env": {"CANVDS_HOME": "D:/myzcanpro", "CANVDS_PYTHON": "D:/py38-32/python.exe"}}}}
```
Claude Code：`claude mcp add canvds -e CANVDS_HOME=D:/myzcanpro -- python D:/myzcanpro/mcp_server.py`

环境变量：`CANVDS_HOME`（放 scan_data 和配置的文件夹，默认本仓库/exe 所在目录）、`CANVDS_PYTHON`（自动拉起 daemon 用的 Python）、`CANVDS_URL`+`CANVDS_TOKEN`（直接指定端口）、`CANVDS_AUTOSTART=0`（禁止自动拉起 daemon）。找端口的顺序：CANVDS_URL → `<HOME>/CanVDS_rpc.json`（界面或 daemon 写入）→ 自动拉起 daemon。

**工具（49 个）**
- 设备/通道：`get_status` `device_list` `device_open` `device_close` `channel_start` `channel_stop`
- UDS：`uds_request` `read_did` `write_did` `read_dtc` `clear_dtc` `ecu_reset` `session_control` `security_unlock` `keepalive_start` `keepalive_stop`
- 软件扫描：`list_modules` `scan_module` `run_function`
- 创建模块/功能（含从报文生成烧写功能）：`get_function_format` `analyze_trace` `create_module` `check_function` `save_function` `read_function` `delete_function`，执行用 `start_function` `function_status` `stop_function`（后台执行，适合耗时数分钟的烧写）
- 报文：`send_frame` `cyclic_start` `cyclic_stop` `monitor_trace` `monitor_snapshot` `monitor_capture` `monitor_clear` `record_start` `record_stop`
- 设置：`get_settings` `set_settings`（分区 diag / security / log / channel，先校验再原地修改并保存，不合法的值一律拒绝且不改任何东西）

**安全**：端口只接受本机连接（回环地址 + Host 校验 + 拒绝浏览器 Origin）并要求令牌；连接信息文件仅当前用户可读。工具说明不再要求 agent 逐项向你确认——你说做什么它就直接做；只有烧写文件、密钥 DLL、CRC 算法、擦除范围这类必须由你提供的参数，缺了才会问，不会猜。录制只能写日志文件夹，`save_function` 只能写 scan_data 下模块的「功能」文件夹，且默认保存未补全的草稿（补全前不能执行）。

**不支持 MCP 的 agent**：直接 POST 到本机端口（`POST /call {"method": "...", "params": {...}}`，头 `Authorization: Bearer <令牌>`，方法名见 `zdiag/ops.py` 的 METHODS）。

**从报文生成烧写功能**：把烧写时抓的报文（ZCANPro / CanVDS 保存的 CSV、Vector ASC、`7E2 02 10 03 ...` 一行一帧的文本均可）给 agent，它会：`analyze_trace`（重组 ISO-TP、配对请求/响应、忽略总线上其它周期报文；36 传输数据自动折叠）→ 生成步骤草稿（会话/解锁/Flash driver/擦除/下载/CRC/自定义例程/复位/延时，多段下载合并为一个步骤）→ 列出报文里不可能有的待补项（烧写文件、密钥 DLL、CRC 算法）→ 你确认后 `save_function` 存进指定模块的「功能」。已用模拟 ECU 做过闭环：录下一次完整烧写 → 生成功能 → 补全 → 重新烧写成功。在软件扫描窗口里重新打开/刷新模块后可以看到新建的功能。

## LIN 诊断（扫描油泵等 LIN 节点）
UDS over LIN：传输层为 NAD + PCI，主请求帧 0x3C / 从应答帧 0x3D（经典校验和），支持单帧/多帧，复用现有 UDS 客户端（NRC 0x78 等照常处理）。
- 工具（MCP / 本机端口，方法名相同）：`lin_open`（kind=sim 模拟油泵 NAD 21 / kind=zlg）、`lin_close`、`lin_request`（对某 NAD 发任意 UDS，如 `22 F1 87`）、`lin_scan_nodes`（TesterPresent 逐个 NAD 探测）、`lin_scan_pump`（读油泵信息：默认标准标识 DID F187/F189/F18A/F18C/F191/F193/F195，可自定义 DID 与解析方式）。
- 代码：`zdiag/lin.py`（传输、模拟从节点、扫描）、`zdiag/zlglin.py`（周立功 LIN 通道绑定，**尚未接入**：需要设备 SDK 中 zlgcan.h 的 LIN 结构体定义，不能凭记忆猜内存布局）。
- 现状：以上在模拟器上验证；真机需要补 `zlglin.py`，并确认油泵的 NAD、波特率（默认 19200）、校验模式和油泵专有 DID。

## 停止与关闭的优先级
「停止」「通道关闭」「设备关闭」「关闭窗口」永远优先：关闭通道/设备时，先通知占用该通道的任务（扫描、功能、普通发送、文件传输、周期发送、Tester Present）立即中止，再关闭，不再弹「通道正在使用」；停止/关闭窗口不会在界面线程里等待，等 ECU 应答（P2 / 0x78）的过程也每 50 ms 检查一次取消。文件传输被中止后，已收到的部分保留，下次发送同一文件/文件夹自动续传。

## 总线错误诊断（周立功通道）
通道收到错误帧时，会读取控制器状态（TEC/REC、总线关闭、错误码）；判断为**总线关闭**时自动重启通道（最多每秒一次）。文件传输看到错误帧激增（>20 帧/0.25 s）会自动降速、恢复后再提速；长时间无进展时报错信息里带上这些诊断（TEC/REC、重启次数、错误帧数）。窗口里的链路行显示「总线错误帧」「降速」。接收队列上限 10 万帧（无人读取时丢弃最旧的，不再无限增长）。**诊断/自动重启依赖 SDK 的 ZCAN_ReadChannelStatus，尚未在真机验证。**

## 设置
主界面菜单栏右侧「设置」：地址、时间参数、通道、安全访问（全局密钥 DLL、序列号）等，对所有工具生效并永久保存。

## 虚拟总线（多进程，脱机测试）
设备选「虚拟总线(多进程)」：同一台电脑上开两个（或更多）上位机进程，选同一个通道号就接在同一条虚拟 CAN 总线上——一个进程发出的帧，其他进程都能收到（发送方自己收不到，和真实总线一样），各进程的报文监视窗口都能看到；不同通道号是互相独立的总线，可以做双通道传输测试。最先打开的进程自动承载总线（它退出时其他进程会断开）；也可以单独起一个常驻的：`python -m zdiag.netbus [端口]`。端口默认 47010，环境变量 `CANVDS_NETBUS_PORT` 可改，所有进程要一致。不模拟位时序，速度远高于真实总线，只用于功能测试；没有模拟 ECU，不用于 UDS 诊断。`tests/test_netbus.py` 里有两个真实进程互传文件（单/双通道）的测试。

## 文件传输（CAN / CAN FD，自定协议，可断点续传）
主界面「文件传输」页签；也可以让 agent 用 `ft_send` / `ft_receive` / `ft_status` / `ft_stop`（不开界面）。**两端都要运行 CanVDS**：一端选「发送」，另一端选「接收」（先开接收端）。

**自动监视/重连**（默认开，`reconnect`）：点「开始」后，收发双方会一直监视所勾选的通道——通道还没打开（或设备还没连上）就先等待，一打开就自动挂接；传输中设备被拔掉/重新连接、通道被关闭，传输不会失败，只是等待，待你在两端分别把设备连好、通道打开后自动恢复并续传（双通道时一条断了另一条继续，回来后自动重新加入）。这种模式下不会因超时放弃，要结束请点「停止」。关闭 `reconnect` 则恢复原来的“超时报错”行为。
- **任意文件、整个文件夹**：发送文件夹时连同子目录和空目录一起传，对端按相同结构保存；不识别格式，按字节原样传输，结束后用整文件 CRC32 校验，保留修改时间。符号链接跳过。
- **断点续传**：接收端把未完成的文件存成 `<名字>.cftpart`，已收块状态存在 `<名字>.cftmeta`；中断（停止、断线、关程序）后再次发送同一文件/文件夹，只补缺的块。已存在且大小和修改时间相同的文件直接跳过（所以整个文件夹重发也只会传没传完的）。源文件改过则自动从头传。
- **速度**：CAN FD 通道自动用长帧（默认 64 字节，数据帧 3 字节头 + 61 字节净荷；经典 CAN 为 8 字节帧 5 字节净荷）；滑动窗口 + 选择性确认（接收端每 20 ms 汇报一次已收块位图），不是一帧一应答。数据帧和控制帧用不同 CAN ID，控制帧优先级更高。
- **大文件的数据完整性（协议版本 2，收发两端须同一版本）**：每个块带自己的 CRC32，对不上的块在收到时就丢弃并重发；全程结束后再做整文件 CRC32。若整文件 CRC 仍不一致，**不删除已收数据**：双方按 4 MiB 一段比对 CRC，只重发有差异的段并再次校验（最多 3 轮）；仍修不好才丢弃并整个重发。进度文件写入时先 fsync 再替换，断电不会丢进度。
- **双通道**：选两个已启动的通道（两端各接两条线）。文件按块分给两条链路，快的多发；每条链路各自心跳，超过 0.6 s 没有声音就判定掉线，把它名下未确认的块立刻改走另一条（`link_timeout_ms` 可调），链路恢复后自动重新加入。两条都断超过 `idle_timeout_s`（默认 30 秒）会中止并保留进度，之后可续传。
- **CAN ID**：默认 `6A0` 起占连续 3 个（控制 发→收、控制 收→发、数据），两端要一致，且别和总线上其他报文冲突；可改为扩展帧。块大小两端也建议一致（默认 1024 字节，经典 CAN 每块最多 256 帧，所以上限约 1280）。
- **安全**：接收端拒绝绝对路径、`..`、盘符等越出保存目录的路径，磁盘空间不足会拒绝，`.cftpart/.cftmeta` 不接收。
- **同一台设备自测**：用线把通道 0 和通道 1 连起来，agent 可以同时 `ft_receive([1], 目录)` 和 `ft_send([0], 路径)`（同一程序里发送和接收各一个任务）。
- 代码：`zdiag/cft.py`（协议与收发引擎）、`zdiag/ops.py` 的 `ft_*`、`zdiag_ui/ft_window.py`。现状：在内存虚拟总线上验证（含丢帧、中途断开一条链路并恢复、断点续传、文件夹），**还没有在真实 CAN 盒子上跑过**；真机上建议先小文件、单通道试通，再上双通道。
