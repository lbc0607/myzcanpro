# CanVDS — UDS 诊断 / ECU 刷新上位机

基于 ZLG(USBCANFD / USBCAN-II)的自研诊断上位机,界面仿 ZCANPro。

## 运行(源码)
需 **32 位** Python(zlgcan.dll 是 32 位)+ PyQt5。ZCANPro 自带的 `python38` 即可:
双击 `run.bat`(路径不同时先设置环境变量 `PY32`)。
不接硬件时,通道选"模拟ECU(测试)"即可体验全部流程。

## 打包成绿色软件
- 本地:双击 `build.bat` → `dist\CanVDS\CanVDS.exe`(整个文件夹拷走即可)。
- 云端:推送到 GitHub 后由 `.github/workflows/build.yml` 构建,在 Actions 的 Artifacts 下载。

## 设备管理(主界面)
1. 下拉选择设备(USBCANFD 系列 / USBCAN-II / 模拟ECU),点「打开」→ 按钮变为「关闭」(只能在两种状态间切换)。
2. 打开成功后出现各通道行,点「启动」弹出配置:CAN/CAN FD、波特率(kbaud/s)、正常/只听、终端电阻、是否计算总线负载率(刷新时间默认 200 ms)。
3. 通道启动后,主界面实时显示接收/发送/错误帧数和总线负载率;UDS诊断、ECU刷新窗口里的「通道」下拉只列出已启动的通道。

## 部署目录(与 exe 同级)
- `zlgcan.dll` 与 `kerneldlls\`:仓库 `vendor\` 里已带官方 SDK(zlgcan_x86,2026-10 版),打包时自动复制到 exe 旁;
  源码运行时程序也会自动在 `vendor\` 里查找。官方头文件在 `docs\zlgcan_sdk_headers\`。
- 公司密钥 dll 及其依赖;需安装 VC++ 2013 x86(zlgcan)、VC++ 2008 x86(密钥 dll)运行库
- 程序运行后自动生成:`CanVDS_config.json`(旧版 myzcanpro_config.json 首次启动自动读取)、`services.json`、`error.log`、`logs\`

## 例程控制(31)
ECU刷新里选 31 服务后，先选「例程类型」，标识符(2 字节)、子服务(01/02/03)都由你填写：
- **擦除内存**: `31 [子服务] [标识符] [44] [起始地址] [大小] [扩展字节]`。格式字节高4位=大小长度、低4位=地址长度(与 ISO 14229 一致，默认 0x44)；
  起始地址、大小取自烧写文件，整个流程只执行一次；扩展字节(默认 01)可编辑或取消；大小可选「各段长度之和」(默认，与校验码工具的总长度一致)或「首段起始到末段末尾」。
- **CRC校验**: `31 [子服务] [标识符] [校验码]`。可选 *分段CRC*(每段传输结束后立刻校验，烧录结束后再做一次全文件CRC) 或 *全文件CRC*(只在烧录结束后校验一次)；
  全文件CRC 为各段按顺序拼接后的校验值。CRC 类型/字节序可配。
- **更新条件查询 / 自定义例程**: 任意 `31 [子服务] [标识符] [数据]`，数据可含占位符 `{addr} {len} {crc}`。

## 方案文件
ECU 刷新方案为 JSON(格式 `myzcanpro-flash`),可自由命名扩展名,各 SID 参数均可编辑。

## 测试

## 报文监视 (Message monitor)
主界面「报文监视」: 实时查看总线上的收发报文，可与 UDS 诊断 / ECU 刷新 / 普通发送同时使用。
- 通道的接收线程每读到一帧，同时交给 UDS 队列和监视器（被动旁听，监视器自己不读设备，不会抢帧，也不改变诊断时序）；发送帧在发送时记录。
- **按ID覆盖显示**（默认）: 同一 ID（通道+方向+ID+帧格式）一行，新帧覆盖旧帧，并显示计数；取消勾选则按时间顺序滚动（最近 1000 帧）。
- **时间差**: 「与同ID上一帧」或「与上一帧(任意ID)」。接收帧使用设备时间戳（保留真实间隔），发送帧用主机时间。
- **实时保存**: 后台线程把每一帧追加写入 CSV（含时间、通道、ID、类型、方向、长度、数据）；「保存」导出当前显示。
- 可按通道 / ID / CAN类型 / 方向 / 数据筛选；「暂停」只冻结显示，计数与保存不受影响。
- **错误帧**: 总线错误帧显示为红色的「错误帧」行（每通道一行，内容显示为 xxx），计数即错误次数，「时间差」即错误帧出现的间隔（频率）；取消底部「显示错误帧」可隐藏；滚动模式下每个错误帧各占一行。能否收到错误帧取决于设备/驱动是否上报。

## 软件扫描 (多核板上各软件的信息/功能)
主界面「软件扫描」: 对板子上的各个软件（动力域控制器 7E2、驱动电机控制器 7E3、电驱充电模块 7E3、从驱动电机控制器 745，响应=物理+8，功能 7DF）读取 软件编码 / 软件版本 / 硬件版本 / 故障码数量。
- **列表页**: 左侧勾选，底部「开始扫描 / 停止扫描」；未读取或读取失败显示 `-`；点软件名称改地址，点任一信息格子进入该项的「读取方式」编辑页；最右 `›` 进入该软件的功能页。
- **功能页**（上下级页面，不是弹窗，「‹ 上一级」返回）: 每个功能是一个按钮，点击即运行；「添加功能」进入编辑页（与 ECU刷新 的编辑器相同：编排 UDS 服务），「新建文件夹」建子菜单（点进去就像进文件夹）；「管理」模式下点按钮可编辑 / 重命名 / 删除。
- **执行器 = 一个 JSON 文件**（服务序列 + 结果显示：取哪一步的回复、跳过开头几个字节，当前只支持十六进制原文）。例如读 VIN：`10 03` + `22 F1 90`，回复 `62 F1 90 XX…XX` 显示为 `XX…XX`。
- **数据文件夹**（默认程序目录下 `scan_data`，可在界面里改）的层级就是界面层级: `<软件>/module.json`、`<软件>/信息/软件编码.json…`、`<软件>/功能/…`。首次运行自动生成上面 4 个软件和默认执行器（默认读取命令: 软件编码 `22 F1 94`、软件版本 `22 F1 95`、硬件版本 `22 F1 93`，故障码数量 `19 01 08`；已存在的 scan_data 里的旧执行器不会被覆盖，要么在界面里改，要么删掉对应 json / 整个 scan_data 重新生成）。
- 扫描/运行时占用所选通道，期间 UDS诊断/ECU刷新 窗口不能同时使用该通道（结束后自动释放）。

## 主界面布局
菜单（设备管理 / UDS诊断 / ECU刷新 / 软件扫描 / 普通发送 / 报文监视 / 校验码计算工具）在界面上方，点击后在界面内新开一个标签页（标签栏在下方，再次点击只切换到已打开的标签）；「设备管理」标签固定不可关闭。标签页右下角「⇱ 浮动」或双击标签可把该页变成独立窗口（窗口里「⇲ 停靠回主窗口」放回标签栏）。关闭标签即关闭该工具；正在刷写时会拒绝关闭。

## CAN FD 说明
- ISO-TP 单帧：≤7 字节的请求按经典单帧格式（`03 22 F1 90 ...`，8 字节 FD 帧）发送；8~62 字节才用扩展单帧头（`00 LL ...`）。早期版本把短请求也写成 `00 03 22 F1 90`，不符合 ISO 15765-2，ECU 不会应答。
- 「CANFD加速」在通道启动配置里（和 ZCANPro 一致）：选「否」时数据域沿用仲裁域波特率、所有 FD 帧不带 BRS；选「是」时数据域用所填速率、帧带 BRS。ECU 与总线上其它节点必须一致。「ISO-TP FD 帧长度」设为 8 则在 FD 通道上改发经典 CAN 帧（ECU 只认经典帧时用）。设置页里原来的「BRS」勾选和「模拟ECU 新/老产品」选项已删除（模拟 ECU 固定用 16 字节 seed）。

## 安全访问 (密钥 DLL 与 EcuSerialNum.txt)
计算密钥的 DLL（`ZLGKey`）每次调用都会读取**其工作目录**下的 `EcuSerialNum.txt`。文件名、所在文件夹（即 DLL 工作目录，默认=程序目录；可填绝对路径，也可点「python.exe所在文件夹」）、序列号 DID、格式、编号映射表都在「更多设置 → 安全访问」，**全程序共用一份并自动保存**（UDS诊断 / ECU刷新 / 软件扫描里打开都是同一份，改一处处处生效，重新打开不会被方案文件覆盖；27 步骤里不再有单独的工作目录）。
- **第 1 行** 序列号：本次运行里**第一次**安全访问前用 `22 <DID>` 读取（默认 `F1 8C`，设置 → 安全访问 可改 DID / 文件名 / 序列号格式 ASCII 或十六进制）并写入；之后的安全访问（含其他 ECU）不再读取，第 1 行保持不变。ECU 消极应答 → 第 1 行为空（视为已读取，不再重试）；读取超时无应答 → 第 1 行为空，但下次安全访问会再试一次。
- **第 2 / 3 行** 软件编号：按**被解锁 ECU 的物理地址**查「设置 → 安全访问 → 编号映射表」，种子 2 字节时 DLL 取第 2 行，16 字节时取第 3 行。默认 `7E2:[0,0]  7E3:[1,2]  785:[2,4]  645:[1,3]`，可增删行；**物理地址不在表里会直接报错**（不发送、不写文件，避免错误密钥消耗 ECU 尝试次数）。
- 读序列号发生在 `27` 的 seed/key 事务**之前**且不占用请求锁，所以会话保活（3E 80）不受影响；seed 与 key 仍在同一个锁内连续完成。
- 程序启动时和退出时都会删除该文件；是否删除不影响正确性（"是否已读取"是每次运行的内存状态，第一次安全访问一定会重写第 1 行）。
- 原先在安全访问步骤里的「通过 F1 8C 写入序列号」勾选项已取消，以此处为准。旧的配置文件如果保存了旧的映射关系，请在设置表里核对。

## 日志与报文保存、普通发送次数
- **日志窗口只显示请求 / 响应（含否定响应）**；步骤横幅、"完成/信息" 行不再输出（步骤状态在刷写步骤列表里看）。出错信息（ERR）和「显示原始帧」打开时的 CAN 帧仍会显示。
- **实时保存按文件大小分片**（参考内部上位机的 MyLogRecord）：设置 → 高级设置 → 输出信息：日志文件夹（默认 `logs`）、单个文件最大 MB（默认 3，1~1024）、保留天数（默认 7，0=不删除，最大 3650）。超过大小自动写到 `xxx_1.txt / xxx_2.txt …`；报文监视的实时保存同样按大小分片（每片带表头）。自动命名的日志（`uds_ / flash_ / monitor_` 开头的 txt/csv，在日志文件夹里）超过保留天数在程序启动和开始保存时删除，其它文件不碰。「输出信息最大行数」上限 1,000,000，「单个文件最大行数」上限 10,000,000。
- **普通发送**：发送次数 1~100,000,000，**-1 = 一直发送**（点「停止」结束）；每次发送帧数 1~1000；间隔 0~3,600,000 ms。时间表按需生成，不再一次性展开（之前把次数设成几百万会占满内存导致崩溃）。串行模式下一直发送的行之后的行不会执行。

## 流程编排（把多个界面的操作拼成一个一键执行的流程）
主界面顶部「流程编排」。默认显示**流程图**（准备 + 每个通道一条纵向泳道；条件分支为菱形，「是 / 否」两路并排后汇合；循环为虚线框并带回路箭头），点击选中、双击编辑，执行时方框变蓝/绿/红/灰并在悬停提示里显示返回信息；右上「切换到列表」可看缩进列表。两种视图共用同一选择，添加/编辑/删除/上移/下移/复制/禁用都可用。**每个通道一条「泳道」，各泳道同时执行**；最前面的「准备」依次执行（打开设备、配置并启动通道），准备失败则不执行泳道。
- **步骤类型**：软件扫描（选模块和字段）、执行功能（引用该模块 `scan_data` 里的功能）、UDS 请求（任意报文，带「复位 / 读故障码 / 清除故障 / 读VIN」常用项，可选先进扩展会话，结果可按 十六进制 / ASCII（如 VIN）/ 十进制 显示）、延时、周期发送报文 + 停止周期发送、条件分支、循环、备注。
- **条件**用下拉选择：「如果 步骤X 的 [结果 或 扫描字段(如故障码数量)] 〔执行成功 / 失败 / 为空 / 不为空 / 等于 / 不等于 / 包含 / 大于 / 大于等于 / 小于 / 小于等于〕 值」，数值比较按返回字节（大端）计算。分支有「成立时 / 否则」两个子列表（例：故障码数量 > 0 才清除；某步失败走另一分支——该步要把「失败后」设为「继续往下执行」，默认是「停止本泳道」）。
- **循环**：固定次数；或「条件成立时重复 / 重复直到条件成立」（有最多次数上限，防止死循环）。
- **执行**：点「▶ 执行」；每个步骤按 执行中(蓝) → 成功(绿) / 失败(红) / 跳过(灰) 变色，并在右侧列显示返回信息（扫描结果、功能返回、ASCII 的 VIN、周期发送共发了多少帧……）。「■ 停止」随时中止，周期发送与通道占用会一并释放。一条泳道失败只停止它自己，其它泳道继续。
- **保存 / 发给别人**：保存为 JSON 流程文件，对方「打开」后点执行即可。流程里**引用本机 `scan_data` 的模块与功能名称**，所以对方电脑上要有同名的模块/功能（打开时会检查并提示缺哪些）；密钥 DLL 等仍用对方本机设置。`examples/示例流程.json` 是按「两个模块扫描 → 读/清故障码 → 复位 → 延时 3 秒 → 重读，同时另一通道周期发送」搭好的示例。
- 同一通道只能有一条泳道；设备已打开时「打开设备」沿用，已启动的通道沿用当前配置。

## 用对话生成流程（MCP / 命令行，任何 agent 都能用）
让 agent 看着本机有哪些模块/功能，直接生成、校验、保存、试跑流程；生成的文件在 CanVDS「流程编排 → 打开」里就能看到流程图。

**MCP 服务**（标准 stdio，Claude Desktop / Claude Code / 其他支持 MCP 的 agent 通用；需要 Python ≥ 3.10）
```
pip install -r requirements-mcp.txt
python mcp_server.py
```
通用配置（各家客户端的 `mcpServers` 写法一致，路径改成你自己的）：
```json
{"mcpServers": {"canvds-flow": {"command": "python", "args": ["D:/myzcanpro/mcp_server.py"],
  "env": {"CANVDS_HOME": "D:/myzcanpro", "CANVDS_PYTHON": "D:/py38-32/python.exe"}}}}
```
Claude Code 也可：`claude mcp add canvds-flow -e CANVDS_HOME=D:/myzcanpro -- python D:/myzcanpro/mcp_server.py`

环境变量：`CANVDS_HOME`（放 scan_data 的文件夹，默认本仓库/exe 所在目录）、`CANVDS_FLOW_DIR`（流程保存位置，默认 `<HOME>/flows`）、`CANVDS_PYTHON`（`run_flow` 用哪个 Python 执行：连真机需要能加载 zlgcan.dll 的 32 位 Python，MCP 服务本身可以跑在别的 Python 上）。

工具：`get_flow_format`（格式说明+示例）、`get_catalog`（本机模块/功能/设备）、`validate_flow`（逐条错误+大纲）、`save_flow`（只写 flows/ 下，校验通过才保存）、`load_flow`、`list_flows`、`run_flow`（无界面执行并返回每步结果；`simulate=true` 先用模拟 ECU 试跑）。

> ⚠ `run_flow` 不带 simulate 会真实操作设备和总线，并与 CanVDS 界面互斥（同一设备只能被一个程序打开）。工具说明里要求 agent 先征得你同意。

**命令行**（不支持 MCP 的 agent 通过 shell 调用，只用标准库，32 位 Python 3.8 可用）：
`python -m zdiag.cli format | catalog | list | check FILE | outline FILE | run FILE [--simulate] [--timeout 300]`，输出 JSON，退出码 0=成功 1=失败 2=用法/文件错误。
