# 0 文档说明

## 0.1 目的

本文档定义 CanVDS 上位机中「文件传输」功能所使用的自定义协议（简称 **CFT**，CAN File Transfer）。
按本文档独立开发的上位机（或嵌入式程序），应能与 CanVDS 上位机互相传输文件，且互为发送方或接收方。
本文档可在无互联网环境下独立使用，不依赖任何外部规范；唯一用到的外部算法是标准 CRC-32（见附录 A）。

## 0.2 术语与用语

| 用语 | 含义 |
|---|---|
| 须 / 不得 | 强制要求，不满足则无法互通或不符合本规范 |
| 应 | 强烈建议，不满足可能影响可靠性、速度或兼容性 |
| 可 | 可选 |
| 发送方 / 接收方 | 一次传输中，发数据的一端 / 收数据的一端。一次会话中角色固定 |
| 链路（link） | 一条 CAN 或 CAN FD 通道（一个设备的一个通道）。两个对端之间可用 1 条或多条链路并行 |
| 块（chunk） | 文件按固定字节数切成的片，是确认、重传、续传的最小单位 |
| 流（stream） | 一个块的数据后面附 4 字节块 CRC，称为该块的「流」 |
| 会话（session） | 从 HELLO 到 BYE 的一次传输，可含多个文件/文件夹 |
| epoch | 1 字节的「文件代号」，用来区分同一会话中先后传输的文件（见 4.2） |

## 0.3 字节序与数值

- 协议中所有多字节整数一律为 **大端（高字节在前）**。
- `u8 / u16 / u32 / u64` 表示无符号整数的位数。
- 字符串一律 **UTF-8**，不带结尾 0，长度由前面的长度字段给出。
- 十六进制写作 `0x..`；示例报文以十六进制字节串给出。

## 0.4 兼容等级

| 等级 | 要求 | 说明 |
|---|---|---|
| **L1 基本互通** | 实现第 3~8 章、第 10 章必需部分；单条链路；经典 CAN 或 CAN FD 均可 | 能完整传输单个/多个文件和文件夹 |
| **L2 完整互通** | L1 + 多链路 + 断点续传 + 分段修复（第 9 章） | 与 CanVDS 全部功能互通 |

没有特别说明时，本文档的「须」均属 L1，标注【L2】的属于 L2。

# 1 系统概述

```
 发送方 (Sender)                                   接收方 (Receiver)
 ┌──────────────┐   CAN ID = base     (控制 S→R)   ┌──────────────┐
 │  文件读取     │ ───────────────────────────────▶ │  文件写入     │
 │  切块 + CRC   │   CAN ID = base+2   (数据 S→R)   │  收块 + 校验  │
 │  滑动窗口     │ ───────────────────────────────▶ │  回状态位图   │
 │  重传 / 修复  │ ◀─────────────────────────────── │  回应用消息   │
 └──────────────┘   CAN ID = base+1   (控制 R→S)   └──────────────┘
```

主要特点：

1. 不使用 ISO-TP（ISO 15765-2）。协议自带分片、确认、滑动窗口。
2. 双通道（多链路）并行：块从同一个队列取，哪条链路快就多发；一条链路断线，其余链路接管。
3. 每个块自带 CRC-32；整个文件另有 CRC-32；整文件校验失败时只按段重传出错的部分。
4. 断点续传：接收方用 `.cftpart` + `.cftmeta` 保存进度，断线、关机后同一文件再发，从中断处继续。
5. 可传文件夹（保持目录结构）。

# 2 角色与总体流程

## 2.1 一次会话

```
Sender                                          Receiver
  │── HELLO (版本, 文件数, 总字节, 窗口, nonce) ──▶│
  │◀────────────── HELLO_OK (版本, 状态, 窗口) ────│
  │                                                │
  │  对每一个条目（目录或文件）依次：                  │
  │── OFFER (epoch, 类型, 路径, 大小, 时间, 头CRC…)▶│
  │◀──────────── REPLY (epoch, 动作, 起始块号) ─────│
  │                                                │
  │  [仅文件且动作=接收]                             │
  │══ 数据帧(块0…n-1) ═══════════════════════════▶ │
  │◀═══ STATUS 位图（每 20 ms） ════════════════════│
  │── END (epoch, 文件大小, 文件CRC32) ───────────▶│
  │◀─────────────── RESULT (epoch, 结果) ───────────│
  │      结果=2(CRC不一致) → 进入第9章修复流程       │
  │                                                │
  │── BYE ────────────────────────────────────────▶│
```

## 2.2 与链路无关的约定

- 发送方、接收方各自独立决定使用哪些链路，**两端使用的链路数不必相等**；每条链路上收到的帧都应被处理。
- 两端的 `base_id`、帧类型（经典 CAN / CAN FD）、块大小应当一致（见第 11 章）。波特率由用户在设备上设置，协议不涉及。
- 一次只传一个文件（无并行文件）。会话内文件按 OFFER 顺序串行。

# 3 物理层与帧格式要求

## 3.1 CAN ID

使用 3 个连续的 CAN ID，起始值为 `base_id`（默认 `0x6A0`）：

| CAN ID | 名称 | 方向 | 内容 |
|---|---|---|---|
| `base` | 控制帧（S→R） | 发送方 → 接收方 | T_MSG、T_ACK、T_HB |
| `base+1` | 控制帧（R→S） | 接收方 → 发送方 | T_MSG、T_ACK、T_STATUS |
| `base+2` | 数据帧 | 发送方 → 接收方 | 文件数据 |

- 默认为标准帧（11 位 ID），`base` 范围 `0x000~0x7FD`；可配置为扩展帧（29 位 ID），范围 `0x00000000~0x1FFFFFFD`。两端须一致。
- 这 3 个 ID 不得被总线上其他报文占用。

## 3.2 帧类型与长度

| 链路类型 | 帧长 `L` | 说明 |
|---|---|---|
| 经典 CAN | 8 | 固定 8 字节，收发都按 8 字节 |
| CAN FD | 12 / 16 / 20 / 24 / 32 / 48 / 64（默认 64） | 同一条链路上所有 CFT 帧的长度固定为 `L`；FD 帧应置 BRS（比特率切换），但接收方不得依赖 BRS |

规则：

1. **数据帧、T_STATUS** 始终发满 `L` 字节（后部补 `0x00`）。
2. **T_MSG、T_ACK、T_HB** 在 CAN FD 上也补 `0x00` 到合法的 DLC 长度；在经典 CAN 上发送其实际长度（T_ACK 为 2 字节、T_HB 为 2 字节，T_MSG 为 4+负载长度）。接收方须按「实际收到的字节数」解析，并容忍尾部多余的 `0x00`。
3. 不得发送 RTR（远程帧）；收到 RTR 须丢弃。
4. 同一条物理总线上的两端须使用同一种帧类型和同一个 `L`（例如不能一端 FD 64、另一端经典 8）。

派生量（后文使用）：

| 符号 | 公式 | 经典 CAN | FD 64 |
|---|---|---|---|
| `P`（数据帧负载） | `L − 3` | 5 | 61 |
| `F`（消息分片负载） | `L − 4` | 4 | 60 |
| `S`（STATUS 位图字节数） | `L − 6` | 2 | 58 |

# 4 帧格式

## 4.1 帧类型字节

控制帧（`base`、`base+1`）的第 0 字节是类型：

| 值 | 名称 | 方向 |
|---|---|---|
| 1 | T_MSG | 双向（可靠消息分片） |
| 2 | T_ACK | 双向（消息确认） |
| 3 | T_HB | S → R（心跳） |
| 4 | T_STATUS | R → S（接收状态位图） |

## 4.2 数据帧（CAN ID = `base+2`，S → R）

```
字节:   0        1            2          3 ... L-1
      [epoch] [chunk&0xFF] [frame_idx] [payload × P 字节]
```

| 字段 | 长度 | 说明 |
|---|---|---|
| epoch | 1 | 当前文件的代号（`1..255`，见 7.2）；接收方丢弃 epoch 不等于当前文件 epoch 的帧 |
| chunk&0xFF | 1 | 块序号的低 8 位（块序号为 u32，见下） |
| frame_idx | 1 | 本块的「流」中第几帧，从 0 开始，**最大 255** |
| payload | `P` | 流中 `frame_idx×P … frame_idx×P+P−1` 的字节，最后一帧不足 `P` 则补 `0x00` |

**块的流（stream）** = 块数据（`clen` 字节） + 块 CRC（4 字节，大端）：

```
stream = chunk_data || BE32( CRC32(chunk_data) )
```

- 块序号 `k`（从 0 开始）对应文件偏移 `k × chunk_bytes`；块数据长度 `clen = min(chunk_bytes, size − k×chunk_bytes)`；最后一块可以更短。
- 一个块占用的帧数 `nf = ceil((clen+4)/P)`，最多 256 帧。因此 **`chunk_bytes + 4 ≤ 256 × P`**：经典 CAN 下 `chunk_bytes ≤ 1276`；FD 64 下 `chunk_bytes ≤ 15612`（本实现限制为 64~15000）。
- 同一个块的帧必须按 `frame_idx` 递增发送，但接收方须容忍乱序、丢失和重复。块的所有帧到齐后才校验。
- 块序号的低 8 位足以区分，因为任何时刻在途的块序号都落在 `[base, base+window)` 内且 `window ≤ 128`（见 8.1）。接收方还原块序号：

```
cand = base + ((lo - base) & 0xFF)       // base 为接收方当前「第一个缺失的块」
若 cand − base ≥ window 或 cand ≥ n 或 cand 已收到 → 丢弃该帧
```

- 接收方收齐一个块的所有帧后，计算 `CRC32(前 clen 字节)` 并与后 4 字节比较：不一致则**丢弃该块**（视为没收到，计数即可），发送方会重发；一致则写入文件并标记已收。
- 块的完整性仅由块 CRC 保证；CAN 帧本身的 CRC 在链路层已校验。

## 4.3 T_MSG —— 可靠消息分片（`base` 或 `base+1`）

应用消息（见第 6 章）可能超过一帧，使用分片传输：

```
字节:   0        1       2              3          4 ... 
      [T_MSG=1] [mid] [frag_idx|last] [plen]  [payload × plen 字节]
```

| 字段 | 说明 |
|---|---|
| mid | 消息号，`1..255` 循环（255 之后回到 1，不使用 0）；起始值任意（CanVDS 每次启动随机），下文示例取 1 |
| frag_idx | 低 7 位：分片序号，从 0 开始；最多 128 个分片（0..127） |
| last | 最高位 `0x80`：置 1 表示这是最后一个分片 |
| plen | 本分片负载长度，≤ `F`（`L−4`） |
| payload | 消息体的一段 |

**消息体 = `[kind (1 字节)] || 应用负载`**；`kind` 见第 6 章。消息体按每片 `F` 字节顺序切开。一条消息最多 `128 × F` 字节（经典 CAN 下 512 字节；FD 64 下 7680 字节）。

接收端重组规则（按「链路 + mid」独立重组）：

1. 收到 `frag_idx = 0` 或 `mid` 与当前正在重组的不同 → 开始新的重组。
2. 缓存每个分片，直到收到 `last` 分片且 `0..frag_idx` 全部到齐，拼成消息体。
3. 重组完成后立即回 **T_ACK**（见 4.4），然后把消息交给上层（去重规则见 5.2）。

## 4.4 T_ACK —— 消息确认

```
[T_ACK=2] [mid]
```

收到并完整重组一条消息后，在**收到该消息的那条链路**上用对向的控制 ID 回发 T_ACK：

- 接收方 → 发送方：CAN ID `base+1`。
- 发送方 → 接收方：CAN ID `base`。
- **重复收到的消息（重传）也须再次回 T_ACK**，但不得再次交给上层（见 5.2）。

## 4.5 T_HB —— 心跳（S → R，`base`）

```
[T_HB=3] [link_idx]
```

发送方每条链路每 `hb_ms`（默认 100 ms）发一帧，用来让接收方知道该链路上有发送方存在（接收方据此决定是否在该链路上发 STATUS）。`link_idx` 仅供调试，接收方可忽略其值。任何从对端收到的帧（心跳、数据、消息）都会刷新「该链路最近收到时间」。

## 4.6 T_STATUS —— 接收状态位图（R → S，`base+1`）

```
字节:   0           1        2..5        6 ... L-1
      [T_STATUS=4] [epoch] [base u32] [bitmap × S 字节]
```

| 字段 | 说明 |
|---|---|
| epoch | 当前接收文件的 epoch；没有正在接收的文件时为 `0` |
| base | 接收方「第一个缺失的块」序号：所有序号 `< base` 的块均已收到并写入 |
| bitmap | 第 `i` 位（第 `i/8` 字节的第 `i%8` 位，LSB 优先）为 1 表示块 `base+1+i` 已收到（乱序到达） |

- 位图只描述 `base+1 … base+8S`；`base` 本身按定义是未收到的。
- 经典 CAN：`S=2`，可报告 16 个块；FD 64：`S=58`，可报告 464 个块，但窗口限制为 ≤128（见 8.1）。
- 无活动文件时发 `[4][0][0 0 0 0][全 0]`，作为在线信号。
- 接收方每 `status_ms`（默认 20 ms）对每条「最近 2 秒内收到过发送方帧」的链路各发一次 STATUS；**没听到发送方的链路不要发**（避免在空总线上喊话）。
- 发送方收到 `epoch = 0` 或 `epoch ≠ 当前文件 epoch` 的 STATUS 须忽略。

# 5 可靠消息层（Messenger）

应用消息（第 6 章）通过「停等 + 重传」可靠传输。**同一时刻每个方向只允许有一条消息在途**。

## 5.1 发送规则

```
send_message(kind, payload, timeout, tries):
    mid = next_mid()                    // 1..255 循环
    per_try = max(timeout / tries, 0.2) // 每次等待 ACK 的秒数
    repeat tries 次:
        对每条「可用」链路（没有可用链路时对所有链路）:
            把 [kind]||payload 按 4.3 分片，全部发送
        等待 T_ACK(mid) 最长 per_try 秒 → 收到则成功返回
    失败 → 报告「对端没有应答」，终止本次会话（或按 12 章处理）
```

- 「可用链路」：发送方侧 = 最近 `link_timeout`（0.6 s）内收到过对端帧的链路；接收方侧 = 最近 2 s 内收到过发送方帧的链路。
- 同一次发送，**同一条消息会在所有可用链路上各发一份**（多链路冗余），对端用 mid 去重。
- 各消息的 `timeout/tries` 取值见第 6 章（总时间 ≈ `timeout`）。

## 5.2 接收去重

- 维护最近 32 个已交付的 `mid`；若新消息的 `mid` 在其中，**只回 T_ACK，不再交给上层**——但 `HELLO` 例外（HELLO 由其 `nonce` 去重，见 6.1）。
- 同一条消息可能经两条链路各到一份、或因 ACK 丢失而重传，去重保证上层只处理一次。
- 消息号循环使用 1..255，在途消息最多 1 条，因此 32 项历史足够。

## 5.3 上层等待

「期望收到某类消息」（如发送 OFFER 后等 REPLY）的等待可按各消息给定的超时处理；收到其他类型的消息应忽略或按状态机处理。

# 6 应用消息定义

消息体 = `kind(1) || 负载`。下表中负载字段均为大端。

| kind | 名称 | 方向 | 说明 |
|---|---|---|---|
| 1 | HELLO | S→R | 开始会话 |
| 2 | HELLO_OK | R→S | 接受/拒绝会话 |
| 3 | OFFER | S→R | 提议传输一个条目（目录/文件） |
| 4 | REPLY | R→S | 对 OFFER 或 REPAIR 的回应 |
| 5 | END | S→R | 文件的块全部确认后，请求最终校验 |
| 6 | RESULT | R→S | 最终校验结果 |
| 7 | BYE | S→R | 会话结束（无负载） |
| 8 | SEGQ | S→R | 分段 CRC 查询（修复） |
| 9 | SEGR | R→S | 分段 CRC 应答（修复） |
| 10 | REPAIR | S→R | 重传某个块区间（修复） |
| 11 | DISCARD | S→R | 放弃该文件，丢弃已收数据 |

## 6.1 HELLO（kind=1）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | version | 协议版本，本文档为 `2` |
| 1 | 4 | nfiles | 本次会话中的**文件**个数（不含目录） |
| 5 | 8 | nbytes | 全部文件总字节数 |
| 13 | 2 | window | 发送方希望的窗口（块数，1~128） |
| 15 | 4 | nonce | 随机数，用于区分不同会话 |

- 发送方：`timeout=10 s, tries=20`（每 0.5 s 重发一次，可持续等待接收方上线）。
- 接收方：若 `nonce` 与上一个已处理的 HELLO 相同 → 是重复的 HELLO，忽略（但应已回过 T_ACK）；否则开始新会话：关闭正在接收的文件（保存进度）、清零统计，随后回 HELLO_OK。
- 接收方可接受任意个会话（一次会话结束后可再接收下一个 HELLO，除非配置为只接收一次）。

## 6.2 HELLO_OK（kind=2）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | version | 接收方协议版本 |
| 1 | 1 | status | `0` 接受；非 0 拒绝（版本不一致或忙） |
| 2 | 2 | window | 接收方采纳的窗口 = `min(HELLO.window, 128)` |

- 接收方：`timeout=6 s, tries=10`。
- 发送方：`status≠0` 或 `version≠2` → 会话失败；有效窗口 `window_eff = min(自身窗口, HELLO_OK.window)`。

## 6.3 OFFER（kind=3）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | epoch | 本条目的文件代号（见 7.2）；目录用 0 |
| 1 | 1 | kind | `0`=文件，`1`=目录 |
| 2 | 4 | index | 条目在本次会话中的序号（仅供显示） |
| 6 | 8 | size | 文件字节数；目录为 0 |
| 14 | 8 | mtime_ms | 修改时间，自 1970-01-01 UTC 起的毫秒数 |
| 22 | 4 | head_crc | 文件前 `min(size, 4096)` 字节的 CRC-32；目录为 0 |
| 26 | 2 | chunk | 块大小（字节） |
| 28 | 2 | plen | 路径字节数 |
| 30 | plen | path | 相对路径，UTF-8，**用 `/` 分隔**，不得以 `/` 开头 |

- 发送方：`timeout=10 s, tries=10`，之后等待 REPLY，最长 20 s（持续运行模式下可无限等待）。
- 路径安全规则（接收方**须**检查，任一不满足则回 `REJECT`）：
  1. 按 `/` 切分；每一段不得为空、`.`、`..`；
  2. 每一段不得含 `:`、`\`、`NUL`，长度 ≤ 255 字节；
  3. 最后一段不得以 `.cftpart` 或 `.cftmeta` 结尾；
  4. 解析后的最终路径必须仍在接收目录之内（防目录穿越、符号链接逃逸）；
  5. 整个路径 UTF-8 编码后 ≤ 1000 字节（发送方遵守）。
- 目录条目：`kind=1`，接收方创建目录后回 `SKIP`。发送方应先发目录条目，再发其内文件；文件夹的顶层名保留，相对路径形如 `顶层/子目录/文件`。发送方不应跟随符号链接，也不发送非常规文件。

## 6.4 REPLY（kind=4）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | epoch | 回显 OFFER 的 epoch（或 REPAIR 的 epoch） |
| 1 | 1 | action | `0`=RECEIVE，`1`=SKIP，`2`=REJECT |
| 2 | 4 | base | action=RECEIVE 时，**已拥有的起始块号**（续传位置，无记录则 0） |
| 6 | 0~200 | text | UTF-8 说明文字，最多 200 字节 |

- 接收方：`timeout=10 s, tries=10`。
- **RECEIVE**：接收方已打开 `.cftpart`，准备好接收块；发送方从 `base` 开始发送（`base` 之前的块视为已收到；接收方另外可能已有「乱序已收」的块，通过 STATUS 位图告知）。
- **SKIP**：发送方不必发送此条目（目录已创建 / 对端已有相同文件 / 已有同名文件且不覆盖）；文件计为跳过，字节数计入进度。
- **REJECT**：该条目失败（路径非法、磁盘空间不足、无法创建文件等），`text` 给出原因；发送方记入失败列表，**继续**下一个条目。

## 6.5 END（kind=5）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | epoch | 当前文件 epoch |
| 1 | 8 | size | 文件总字节数 |
| 9 | 4 | file_crc | 整个文件的 CRC-32 |

- 发送方在 **全部块都被确认**（STATUS 的 `base ≥ n`）后发送：`timeout=10 s, tries=10`；随后等待 RESULT，最长 `wait = 120 s + size / 2·10⁷ s`（大文件接收方需要整文件读一遍计算 CRC）。
- 接收方处理：见 10.3。

## 6.6 RESULT（kind=6）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | epoch | 回显 |
| 1 | 1 | code | `1`=成功，`0`=失败，`2`=整文件 CRC 不一致（进入修复） |
| 2 | 0~200 | text | UTF-8 说明 |

- 接收方：`timeout=10 s, tries=10`。
- `code=1`：该文件完成。`code=0`：失败（如还缺块、写文件失败）。`code=2`：保留已收数据，发送方应进入第 9 章的修复流程。

## 6.7 BYE（kind=7）

无负载。发送方发完所有条目后发送：`timeout=2 s, tries=4`；失败可忽略。接收方收到后关闭当前文件并结束会话。

## 6.8 SEGQ / SEGR / REPAIR / DISCARD（kind=8~11）

见第 9 章。

# 7 传输状态机

## 7.1 发送方

```
IDLE ──(开始)──▶ CONNECTING: 持续发 HELLO 直到 HELLO_OK
CONNECTING ─(HELLO_OK 且版本一致)─▶ NEXT_ENTRY
NEXT_ENTRY:
    还有条目?  否 → 发 BYE → DONE
    条目是目录 → OFFER(epoch=0, kind=1) → 等 REPLY → NEXT_ENTRY
    条目是文件 → 分配 epoch → OFFER → 等 REPLY:
         REJECT → 记失败 → NEXT_ENTRY
         SKIP   → 计跳过 → NEXT_ENTRY
         RECEIVE(base) → SENDING
SENDING: 滑动窗口发块(8.1)，直到 STATUS.base ≥ n
         → 计算整文件 CRC-32 → 发 END → 等 RESULT:
               code=1 → 完成 → NEXT_ENTRY
               code=0 → 失败 → 重发整个文件一次(retries=1)，仍失败则记失败 → NEXT_ENTRY
               code=2 → REPAIR(第9章) → 重发 END → …（最多 3 轮）→ 仍不成功则 DISCARD 后重发整个文件
```

## 7.2 epoch 分配

- 发送方每开始传一个文件（包括「整文件重发」、每一段 REPAIR）时，`epoch = (epoch % 255) + 1`，即在 `1..255` 内循环，**不使用 0**。
- 目录条目的 OFFER 使用 epoch=0，REPLY 回显即可。
- 数据帧、STATUS、END、RESULT、SEGQ、SEGR、REPAIR、DISCARD 都带 epoch，接收方只处理与当前文件 epoch 相同的内容。

## 7.3 接收方

```
WAITING: 等 HELLO → HELLO_OK → RECEIVING
RECEIVING:
    收到 OFFER  → 关闭上一个文件(保存进度) → 按 6.3/10 判定 → REPLY
    收到数据帧  → 收块/校验/写盘
    收到 END    → 10.3
    收到 SEGQ / REPAIR / DISCARD → 第 9 章
    收到 BYE    → 关闭当前文件 → 会话结束(单次模式退出；持续模式回到 WAITING)
    收到 HELLO(nonce 不同) → 放弃当前会话状态，开始新会话
```

# 8 数据传输、窗口与重传

## 8.1 滑动窗口

- 令 `n = ceil(size / chunk_bytes)`（空文件 `n=0`）。发送方维护：
  - `base`：来自 STATUS 的「第一个缺失块」；
  - `acked`：位图确认的块集合；
  - `inflight`：已发出但未确认的块（记录每块的发送时间、所用链路）。
- 在途窗口：`window_eff = min(window, HELLO_OK.window, 8×S)`，其中 `S` 为当前在线链路的 STATUS 位图字节数（两端同类型时就是 `L−6`；CanVDS 取在线链路中的最大值）；且 **`window ≤ 128`**。经典 CAN 下 `8×S=16`，所以有效窗口 ≤16 块。
- 新块序号 `k` 只有在 `k < base + window_eff` 时才可发送。
- 接收方只接受 `[base, base+window)` 内的块，窗口外的帧丢弃。

## 8.2 STATUS 的处理（发送方）

收到 `[T_STATUS][epoch][base][bitmap]`（`epoch` 与当前文件一致）：

1. 序号 `< base` 的块全部视为已确认；
2. 位图中为 1 的位对应块 `base+1+i` 视为已确认；
3. 把当前窗口基线推进到 `base`；
4. 对每个新确认的块，若有发送时间则更新往返时间估计 `srtt = 0.875×srtt + 0.125×样本`；
5. 快速重传：同一条链路上，若某个未确认块的发送序号比该链路上最近被确认的块的发送序号小 3 以上，视为丢失，重新入队；
6. 全部确认（`base ≥ n`）后，该文件的块发送阶段结束，进入 END。

## 8.3 超时重传

- `RTO = max(0.4 s, 3×srtt + 0.1 s)`；块发出超过 RTO 仍未被确认 → 重新入队（可换链路）。
- 同一个块重传时，**整块的所有帧都要重发**（块是最小重传单位）。

## 8.4 多链路【L2】

- 所有链路共享同一个待发队列：各链路的发送线程从队列取下一个块，哪条链路快就取得多。
- 链路判定：发送方在某条链路上超过 `link_timeout`（0.6 s）没收到任何对端帧 → 判定离线，该链路上在途的块全部重新入队，由其他链路接手；离线链路仍每 `hb_ms` 发心跳探测，收到对端帧后自动恢复。
- 发送失败（设备返回错误、发送缓冲满持续超过 1 s）等同离线。
- 所有链路都离线时：发送方可暂停等待重连（上位机的「自动重连」模式），或在 `idle_timeout`（默认 30 s）后放弃。

## 8.5 总线错误降速（建议）

链路上每 0.25 s 统计一次总线错误帧增量：增量 ≥ 20 → 每帧发送前额外等待 `backoff`（从 5 ms 起翻倍，最大 250 ms）；增量 ≤ 2 → `backoff` 减半，直到 0。避免在故障总线上持续冲击。

## 8.6 发送优化（建议）

- 一个块的所有帧用设备驱动的「批量发送」接口一次提交（如 ZLG 的 `ZCAN_TransmitFD` / `ZCAN_Transmit` 的 `len` 参数 >1），帧间无空隙，可明显提高总线利用率。
- 设备发送缓冲满时，以≤0.5 ms 的间隔轮询重试；Windows 下应把系统定时器分辨率调到 1 ms，否则 `sleep(0.5ms)` 会实际睡 ~15 ms。

# 9 完整性校验与分段修复【L2】

整文件 CRC 不一致说明块 CRC 之外仍有损坏（磁盘、内存错误或实现缺陷）。**不要整个文件重来**，按段定位：

## 9.1 参数

- 段大小 `SEG_BYTES = 4 MiB = 4 194 304`。每段包含的块数 `spc = max(1, SEG_BYTES / chunk_bytes)`（整数除法）。
- 第 `s` 段覆盖块 `[s×spc, min(n, (s+1)×spc))`，对应文件字节 `[s×spc×chunk, min(size, (s+1)×spc×chunk))`。总段数 `nseg = ceil(n / spc)`。
- 一条 SEGR 最多携带 `SEG_PER_MSG = 100` 个段 CRC。最多修复 `REPAIR_ROUNDS = 3` 轮。

## 9.2 流程

```
Receiver 回 RESULT(code=2) 之后，保留 .cftpart 与全部已收数据（不删除）。

Sender                                           Receiver
  │── SEGQ(epoch, first_seg, count) ───────────────▶│  接收方第一次被问到时，整文件读一遍，
  │◀─────────────── SEGR(epoch, first, got, crc[]) ─│  计算每段 CRC，之后从内存回答
  │  Sender 本地算同样的段 CRC，与 SEGR 比较，记下不一致的段
  │  对每个不一致的段 [lo, hi)：
  │── REPAIR(新 epoch, lo, hi) ───────────────────▶│  接收方：把 base=lo，n=hi，清空窗口
  │◀──────────────── REPLY(epoch, RECEIVE, lo) ────│
  │══ 数据帧：仅发块 lo … hi-1（新 epoch）═════════▶│  同常规块传输，STATUS 报告 base/位图
  │   （全部确认后，该段结束，接着处理下一个不一致段）
  │── END(最后一次 epoch, size, file_crc) ────────▶│  接收方：区间补齐后恢复整文件范围，再校验
  │◀────────────────────── RESULT ─────────────────│  成功 → 完成；仍为 2 → 进入下一轮
超过 3 轮仍失败 → DISCARD(epoch) → 接收方删除 .cftpart/.cftmeta → 发送方整文件重发一次
```

## 9.3 消息格式

**SEGQ（kind=8）**：`epoch(1) first(4) cnt(2)` —— 查询第 `first` 段开始的 `cnt` 个段的 CRC。

**SEGR（kind=9）**：`epoch(1) first(4) got(2) crc[0..got-1]（各 4 字节）` —— `got ≤ cnt`，取决于实际段数。

**REPAIR（kind=10）**：`epoch(1) lo(4) hi(4)` —— 重传块区间 `[lo, hi)`。接收方须检查 `0 ≤ lo < hi ≤ n_full`，不合法回 `REPLY(REJECT)`；接收方把当前文件的 epoch 改为新 epoch、`base=lo`、`n=hi`，回 `REPLY(RECEIVE, base=lo)`。

**DISCARD（kind=11）**：`epoch(1)` —— 放弃当前文件，接收方删除 `.cftpart` 与 `.cftmeta`。

# 10 接收方文件处理要求

## 10.1 临时文件与进度

- 接收中的文件写成 `<最终文件名>.cftpart`，进度保存在 `<最终文件名>.cftmeta`。完成后把 `.cftpart` 改名为最终文件名并删除 `.cftmeta`。
- 接收区间 `[base, n)` 内乱序到达的块可直接按 `k × chunk_bytes` 偏移写入 `.cftpart`（随机写）。
- `.cftmeta` 为 UTF-8 JSON（【L2】断点续传所需；两端实现各自私有，**不要求跨实现互读**，但同一实现自己须能续传）。CanVDS 的格式：

```json
{"v": 2, "size": 123456, "mtime_ms": 1700000000000, "head": 3000000000,
 "chunk": 1024, "base": 100, "done": [102, 103, 107]}
```

- 每秒最多保存一次（先把 `.cftpart` 刷盘（fsync），再写临时文件并 fsync，最后原子替换 `.cftmeta`），断电后元数据永远不会比数据新。
- 续传条件（全部满足才续传，否则删除 `.cftpart/.cftmeta` 从 0 开始）：`size`、`mtime_ms`、`head_crc`、`chunk` 与 OFFER 一致；`.cftpart` 存在且长度 ≥ `min(size, base × chunk)`；`base ≤ n`。

## 10.2 对 OFFER 的判定顺序（文件）

1. 路径安全检查（6.3）→ 失败回 `REJECT`；
2. 创建上级目录；
3. 若最终文件已存在：`size` 与 `mtime_ms`（毫秒）都相同 → 回 `SKIP`（已有相同文件）；否则若配置为「不覆盖」→ 回 `SKIP`；否则继续（将覆盖）；
4. 读取元数据，决定续传起点 `base` 与乱序已收集合；
5. 磁盘剩余空间 `< 需要字节数 + 1 MiB` → 回 `REJECT`（磁盘空间不足）；
6. 打开 `.cftpart`（续传用 `r+b`，否则新建/截断），保存元数据，回 `RECEIVE(base)`。

## 10.3 对 END 的处理

收到 `END(epoch, size, crc)`：

1. 没有当前文件或 `epoch` 不符 → `RESULT(code=0, "没有对应的文件")`；
2. 若 `base < n`（还缺块）→ `RESULT(code=0, "还缺 N 块")`；
3. 若处于「修复区间」且区间已补齐，恢复为整文件范围；
4. `.cftpart` 截断到 `size`，关闭，**整文件读取并计算 CRC-32**；
5. 文件长度等于 `size` 且 CRC 等于 `crc`：改名为最终文件名，把修改时间设为 `mtime_ms`，删除 `.cftmeta`，`RESULT(code=1)`；
6. 否则保留 `.cftpart` 与已收数据，标记「CRC 不一致」，`RESULT(code=2)`，等待第 9 章的修复；
7. 写文件出错 → `RESULT(code=0, 原因)`。

## 10.4 其他

- 接收方应能同时处理收帧与写盘，不得因为写盘慢而丢弃已校验成功的块；内存中只缓存「正在收齐」的块（`O(window)`），已完成的块立即写盘，不得缓存整个文件。
- 超大文件（十几 GB）：所有文件偏移、大小、块序号用 64 位 / 32 位整数；块序号 u32 → 在 `chunk_bytes=1024` 时可支持约 4 TiB 文件。

# 12 异常与边界处理

| 场景 | 要求 |
|---|---|
| 消息发送 `tries` 次都没有 ACK | 报错并终止会话。已收部分保留，重新发送同一文件可续传 |
| 链路离线 / 设备拔出 | 发送方：在途块重新入队，由其它链路接手；无链路可用时按 8.4 处理。接收方：该链路不再发 STATUS |
| 设备重新连接 | 链路重新打开后立即参与收发（本实现提供自动监视并重连，持续等待到用户停止） |
| 收到未知 `kind` / 未知 T_xxx | 忽略 |
| 收到 `epoch` 不匹配的数据帧/STATUS | 丢弃 |
| 块 CRC 失败 | 丢弃该块，等待重发；累计计数供显示 |
| 重复的 HELLO（同 nonce） | 只回 ACK，不重新开始 |
| 重复的消息（同 mid） | 只回 ACK，不重复处理 |
| 空文件 | `n=0`，OFFER 后接收方回 RECEIVE，发送方直接发 END（无数据帧） |
| 磁盘满 | REPLY(REJECT)；写盘中途失败 → RESULT(0) |
| 路径含非法字符 | REJECT，继续下一个条目 |
| 用户点「停止」 | 立即中止，已收到的块保留；不应等待对端 |

# 13 示例报文（测试向量）

以下均为 **经典 CAN（L=8，P=5，F=4）**、标准帧、`base_id=0x6A0`。用于验证实现。

## 13.1 数据帧

文件内容 = `01 02 03 04 05 06 07 08 09 0A`（10 字节），`chunk_bytes=1024`，只有 1 个块（块 0）；epoch=1。

- `CRC32(01 02 … 0A) = 0x2520577B`
- 流（14 字节）= `01 02 03 04 05 06 07 08 09 0A 25 20 57 7B`
- 共 3 帧，CAN ID `0x6A2`：

| frame_idx | 8 字节数据（十六进制） |
|---|---|
| 0 | `01 00 00 01 02 03 04 05` |
| 1 | `01 00 01 06 07 08 09 0A` |
| 2 | `01 00 02 25 20 57 7B 00` |

（字节 0=epoch，1=块序号低 8 位，2=frame_idx，之后为负载；最后一帧补 `00`）

## 13.2 HELLO（kind=1）

负载：version=2、nfiles=3、nbytes=1000、window=128、nonce=`0x11223344`。
消息体（20 字节）= `01 | 02 | 00000003 | 00000000000003E8 | 0080 | 11223344`，即
`01 02 00 00 00 03 00 00 00 00 00 00 03 E8 00 80 11 22 33 44`。
按 `F=4` 分成 5 个分片，`mid=1`，CAN ID `0x6A0`：

```
01 01 00 04 01 02 00 00
01 01 01 04 00 03 00 00
01 01 02 04 00 00 00 00
01 01 03 04 03 E8 00 80
01 01 84 04 11 22 33 44      ← frag_idx=4 且置 last(0x80) → 第 2 字节 0x84
```

对端完整收到后，用 CAN ID `0x6A1` 回 `T_ACK`：`02 01`。

## 13.3 OFFER（kind=3）

文件 `a.bin`，size=10，mtime_ms=1700000000000(`0x0000018BCFE56800`)，head_crc=`0x2520577B`，chunk=1024，epoch=1，index=0：
消息体 = `03 | 01 | 00 | 00000000 | 000000000000000A | 0000018BCFE56800 | 2520577B | 0400 | 0005 | 61 2E 62 69 6E`

即 `03 01 00 00 00 00 00 00 00 00 00 00 00 00 0A 00 00 01 8B CF E5 68 00 25 20 57 7B 04 00 00 05 61 2E 62 69 6E`（36 字节）。

## 13.4 STATUS

接收方当前 epoch=1，`base=5`，已乱序收到块 6 和块 8（即 `base+1` 与 `base+3`，位图第 0 位、第 2 位）：
`04 01 00 00 00 05 05 00`，CAN ID `0x6A1`。

## 13.5 标准 CRC-32 校验值

`CRC32("123456789") = 0xCBF43926`（用来验证 CRC 实现与 zlib 一致）。

# 14 设计开发要求（给实现者的清单）

## 14.1 必须实现（L1）

| 编号 | 要求 |
|---|---|
| R-01 | 使用 3 个连续 CAN ID（`base`、`base+1`、`base+2`），含义见 3.1 |
| R-02 | 经典 CAN 帧长 8，FD 帧长 `L` 固定；数据帧、STATUS 发满 `L`，其余可按 3.2 处理；不发 RTR |
| R-03 | 所有多字节整数为大端 |
| R-04 | 数据帧格式、块的流（数据+CRC32 大端）、块号还原算法（4.2）与本规范一致 |
| R-05 | 实现 T_MSG 分片/重组、T_ACK 回复、停等重传、mid 去重（第 5 章） |
| R-06 | 实现 HELLO / HELLO_OK / OFFER / REPLY / END / RESULT / BYE 的编解码与流程（第 6、7 章） |
| R-07 | 发送方：滑动窗口 ≤128；STATUS 解析；RTO 重传（第 8 章） |
| R-08 | 接收方：每 20 ms 发送 STATUS；按 `base` + 位图报告；随机写 `.cftpart`；块 CRC 失败丢弃（4.2、4.6、10） |

| T-01 | 本实现作发送方、CanVDS 作接收方：传 10 B / 1 KB / 1 MB / 100 MB 文件 | 对端文件 CRC-32 与源一致，修改时间一致 |

## 14.4 实现建议

- 收发分线程：每条链路 1 个接收线程；发送方每条链路 1 个发送线程；另有定时线程（心跳、STATUS、状态监控）。
- 接收线程里只做解包和入队，不做耗时操作；写盘、整文件 CRC 在另外的线程或在消息处理线程中完成。
- 块的重组缓冲只保存「正在收的块」，用位图记录帧是否到齐；乱序、重复帧须容忍。
- 所有等待都应能被「停止」立刻打断。

# 附录 A CRC-32

使用标准 CRC-32（IEEE 802.3 / zlib / PKZIP）：多项式 `0x04C11DB7`（反射形式 `0xEDB88320`），初值 `0xFFFFFFFF`，输入输出均按位反射，结果异或 `0xFFFFFFFF`。与 Python `zlib.crc32()` 结果相同；`CRC32("123456789") = 0xCBF43926`。

C 语言参考实现（逐字节查表）：

```c
#include <stdint.h>
#include <stddef.h>

static uint32_t crc_table[256];

void crc32_init(void) {
    for (uint32_t i = 0; i < 256; i++) {
        uint32_t c = i;
        for (int k = 0; k < 8; k++)
            c = (c & 1) ? (0xEDB88320u ^ (c >> 1)) : (c >> 1);
        crc_table[i] = c;
    }
}

/* 增量计算：首次 crc = 0，后续把上一次返回值传入 */
uint32_t crc32_update(uint32_t crc, const uint8_t *p, size_t n) {
    crc = ~crc;
    while (n--) crc = crc_table[(crc ^ *p++) & 0xFF] ^ (crc >> 8);
    return ~crc;
}
```

# 附录 B 块号还原与位图示例（伪代码）

```c
/* 接收方：由数据帧的低 8 位还原块号 */
uint32_t chunk_no(uint32_t base, uint8_t lo) {
    return base + (uint8_t)(lo - (uint8_t)base);   /* 等价于 base + ((lo - base) & 0xFF) */
}

/* 接收方：生成 STATUS 位图 */
void build_status(uint8_t *out, uint32_t base, const bool *done /* done[k]: 块 k 已收 */, int S) {
    memset(out, 0, S);
    for (int i = 0; i < 8 * S; i++)
        if (done[base + 1 + i]) out[i >> 3] |= (1u << (i & 7));
}

/* 发送方：解析 STATUS 位图 */
for (int i = 0; i < 8 * S; i++)
    if (bitmap[i >> 3] >> (i & 7) & 1) mark_acked(base + 1 + i);
```

# 附录 C 与 CanVDS 的对应关系与限制

- 协议版本号 `2`（块自带 CRC32）。版本 1 的 `.cftmeta` 仍可用于续传，但线路格式与版本 2 不同，不互通。
- CanVDS 的默认值见第 11 章；块大小、窗口、帧长等在两端不一致时的行为：块大小由发送方通过 OFFER 通知，接收方按 OFFER 的值工作；窗口取两端较小值；帧长 `L` 须相同，否则链路无法互通。
- CanVDS 一个传输任务最多使用 2 条链路；协议本身不限制链路数，但 STATUS 位图、窗口（≤128）等规则不变。
- 一次只传一个文件；协议没有「暂停」帧，暂停即停止，之后用续传恢复。
- 协议不含加密与认证，仅用于可信的内部网络/台架环境。
